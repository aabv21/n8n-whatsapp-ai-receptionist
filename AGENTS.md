# AGENTS.md

Guidance for anyone — human or AI — working in this repository.

## Purpose

This repo builds a WhatsApp AI receptionist for Cumbident, a fictional dental studio, as an n8n workflow backed by Postgres. It is a portfolio demo: every file should read as production-quality, not a prototype.

## Repo map

- `compose.yaml`, `.env.example` — the local runtime: Postgres and n8n in Docker Compose, plus an optional ngrok tunnel.
- `compose.queue.yaml` — an optional override that adds Redis and `n8n-worker` containers for queue mode; see Commands.
- `db/schema.sql`, `db/init/` — the application database's baseline schema and the one-time role/database bootstrap script, both run only on an empty volume.
- `db/migrations/` — every schema change after that baseline, as an idempotent, numbered `NNN_short_name.sql` file that `pnpm run db:migrate` applies once each, recording it in `schema_migrations`: `001_runtime_role.sql` (the least-privilege `app_runtime` role and its grants), `002_route_check.sql` (a `CHECK` on `inbound_messages.route`), and `003_received_at_index.sql` (an index on `inbound_messages (received_at)` for `retention-cleanup`'s age delete).
- `ngrok/traffic-policy.yml` — the tunnel's traffic policy: forwards only the WhatsApp Trigger's own fixed webhook path (`workflows/whatsapp-entry.json`'s `webhookId`), denying every other path, including other webhook-shaped ones, then rate-limits what's left per client IP. `compose.yaml` runs ngrok with `--inspect=false` and caps n8n's request bodies at 2 MiB (`N8N_PAYLOAD_SIZE_MAX`); `tests/runtime.test.ts` pins all three.
- `config/config.example.json` — the config template; a developer's own `config/config.json` is gitignored.
- `scripts/manifest.ts` — the single source of truth for fixed workflow/credential IDs and the `CODE_NODES` table; `scripts/lib/` holds the shared workflow, runtime (Docker/`.env`), dev-harness-client, and scenario-grading (`scenarios.ts`) helpers.
- `scripts/check-workflows.ts`, `scripts/build-workflows.ts`, `scripts/export-workflows.ts`, `scripts/import-workflows.ts`, `scripts/setup-credentials.ts`, `scripts/dev-call.ts`, `scripts/run-scenarios.ts`, `scripts/init-env.ts`, `scripts/check-dev-response.ts`, `scripts/db-migrate.ts`, `scripts/check-db.ts` — the workflow and database tooling CLIs; see Commands below.
- `src/nodes/` — one `run()` function per Code node, compiled into workflow JSON by `pnpm run build:workflows`; `src/nodes/shared/` holds logic more than one Code node reuses (e.g. `opening-hours.ts`, and the language helpers `locale.ts`, `detect-language.ts`, and `team-messages.ts`; see Languages below); `src/globals.d.ts` declares the ambient `DateTime` those sources use.
- `tests/` — Vitest tests; `tests/fixtures/` holds workflow and Code-node fixtures, `tests/helpers/run-generated.ts` runs a generated Code node's output the way n8n's sandbox does, and `tests/scenarios/` holds evaluation sets (`triage.json`, `conversations.json`) that `scripts/run-scenarios.ts` grades through the dev harness.
- `tsconfig.json`, `eslint.config.ts`, `vitest.config.ts`, `package.json` — the TypeScript toolchain.
- `business/business.json`, `business/knowledge-base.md` — the business facts (including every fixed patient reply, as `{ en, es }`) and FAQ prose the workflows read at runtime; `prompts/system-prompt.md` — the assistant's system prompt template (placeholders `<<BUSINESS>>`, `<<KNOWLEDGE_BASE>>`, `<<NOW>>`, `<<LANGUAGE>>`, `<<TRIAGE_NOTES>>`), checked by `tests/content.test.ts`.
- `workflows/` — the n8n workflow JSON, mounted read-only into n8n and imported by `pnpm run setup`. In place: the four platform workflows (`load-context`, `error-handler`, `notify-team`, `dev-harness`), the business tools (`check-availability`, `upsert-patient`, `book-appointment`), `triage-message`, `process-message` (the core every patient message runs through: record, dedupe, resolve the language, rate-limit, triage, route, and the AI Agent with its four tools), `whatsapp-entry` (the WhatsApp webhook entry point in front of it — normalizes the Meta payload, calls `process-message`, and sends its reply back, held back from publishing until a real WhatsApp trigger credential exists), and `retention-cleanup` (a daily, Postgres-only job that deletes `n8n_chat_histories` rows judged by `inbound_messages`, then `inbound_messages` itself, by `config.limits.retention_days`; its Execute Workflow Trigger, alongside the Schedule Trigger, lets the dev harness run it on demand too).
- `docs/database.md` — how the database is run: the roles, every statement the workflows issue and the grant and index behind it (including why the Postgres Chat Memory node connects as the owner role), migrations, retention, backup and restore, connections, the upgrade path for an existing local volume, and what `check-db` proves. Update it when a change adds a query, a table, a grant, or a migration.
- `docs/red-team.md` — where a patient's text reaches a model, every adversarial input with its expected safe behavior and the guard that enforces it (deterministic, with its test, or prompt-only, with why that's accepted), how to run those inputs live, and the questions only a live run answers. Update it when a change adds a model input, a tool, a tool field the model fills, or a guard.
- `docs/architecture.md` — the architecture doc, covering the components, the message lifecycle, the data model, failure modes, scaling and security notes, and the design decisions. Update it when a change alters any of those.
- `docs/testing.md` — every test suite's command, coverage, and how it stays deterministic, plus the stack checks, the scenario and red-team suites, what CI runs, and the deferred live checks. Update it when a change adds or removes a test file, a suite, or a CI step.
- `docs/diagrams/` — the system architecture and message-sequence diagrams. Each `*.json` file is a diagram's source; archify renders the `*.html` page from it, and the `*.svg` image is that page's own SVG export. Edit only the JSON, then regenerate the other two (see Commands).

## Commands

- `pnpm install --frozen-lockfile` — install dependencies from the lockfile.
- `pnpm run typecheck` — `tsc --noEmit`.
- `pnpm run lint` — `eslint .`.
- `pnpm test` — `vitest run`. [docs/testing.md](docs/testing.md) lists every suite and what it covers.
- `docker compose up -d --wait` — start Postgres and n8n, and wait for both to report healthy.
- `docker compose --profile tunnel up -d --wait` — also start the ngrok tunnel (needs `NGROK_AUTHTOKEN` and `NGROK_DOMAIN`).
- `docker compose down` — stop the stack. Add `-v` to also drop the named volumes (destructive: wipes the database and n8n's data).
- `docker compose -f compose.yaml -f compose.queue.yaml up -d --wait --scale n8n-worker=2` — switch to queue mode: adds Redis and the given number of `n8n-worker` containers, which run executions instead of the main process. `n8n-worker` extends `compose.yaml`'s own `n8n` service (same encryption key, database settings, and read-only `/files` mounts), with its published port reset so it scales past one replica without a conflict.
- `docker compose -f compose.yaml -f compose.queue.yaml down && docker compose up -d --wait` — return to the regular, single-process stack. Plain `down`, with no `-v`, keeps the named volumes.
- `pnpm run build:workflows` — bundles each `src/nodes/*.ts` with esbuild into its Code node's `jsCode`, in the workflow file `scripts/manifest.ts`'s `CODE_NODES` names. Add `--check` to fail (exit 1) if the committed JSON doesn't match the source, without writing — that's what CI runs. After an esbuild update, run this and commit the regenerated JSON.
- `pnpm run check` — hygiene checks on every file in `workflows/`: pinned data, a literal email/phone/long id/secret, an unknown credential id, a hand-written or undocumented Code node, a missing required setting, an external-service node without retry on fail, and a Postgres query built from an expression instead of `$n` parameters.
- `pnpm run db:migrate` — applies every pending file in `db/migrations/` (`scripts/db-migrate.ts`), each in one transaction with its `schema_migrations` row, as the Postgres superuser over the `postgres` container's local socket, then sets `app_runtime`'s password from `APP_RUNTIME_DB_PASSWORD` and re-asserts its attributes (`NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`), with `log_min_error_statement` raised to `panic` for that transaction so a failed `ALTER ROLE` never logs its password. Each file's transaction takes a fixed advisory lock first. Stops before touching the database when a file contains a transaction-control statement, when `APP_RUNTIME_DB_USER` shares its name with another role variable, or when a variable a pending file reads with `\getenv` is unset or empty, naming files and variables only. A second run prints `no pending migrations`. Passes each variable to `docker compose exec` as a bare `-e NAME`, so no value ever reaches an argument list. See `docs/database.md`.
- `pnpm run setup` — runs `db:migrate`, then imports credentials (`scripts/setup-credentials.ts`), then publishes workflows (`scripts/import-workflows.ts`) into the local n8n instance. Skips a credential whose `.env` values are blank, or a Google Calendar/Sheets/Gmail credential that already exists (run `node scripts/setup-credentials.ts --force` to overwrite them deliberately — each carries an interactive Google sign-in that `import:credentials` would otherwise wipe out, so a changed Google credential setting, such as the Gmail scope, reaches an existing instance only that way or through the n8n editor; see the README's upgrade steps). Skips a workflow not yet in `workflows/`, and holds back one whose trigger needs a credential that isn't available yet.
- `pnpm run export` — writes n8n's canonical form of every known workflow back to `workflows/` and regenerates their Code nodes; run this after editing a workflow in the n8n UI, and commit the result.
- `pnpm run scenarios -- --triage` — calls `triage-message` once per item in `tests/scenarios/triage.json` (17 English/Spanish messages) through the dev harness and prints a `| lang | signal | correct/total |` accuracy table (`scripts/lib/scenarios.ts`'s `triageAccuracy`, which reuses `decide-route.ts`'s own `>=` threshold rule so the report can't drift from the logic it's grading — a `null` score, from a Jev failure, always counts as wrong). Needs a real TypeSafe credential to mean anything; without one, every score is `null` and every row reads 0.
- `pnpm run scenarios` with no flags — runs the triage table above, then every scripted, multi-turn conversation in `tests/scenarios/conversations.json` through `process-message`, checking each turn's route, tools called or excluded, reply text, and tool input/output against that scenario's expectations (`scripts/lib/scenarios.ts`'s `checkTurn`, with `nextWeekday` and `resolveTokens` resolving `{{next_thursday}}`-style relative dates), and prints a `| id | result | details |` table. `cleanup` with prefix `5700000000` runs before and after the conversation batch. A scenario marked `requires_open_tomorrow` prints `SKIP` instead of running when tomorrow is a Sunday in America/Bogota. The process exits 1 only when a conversation is `FAIL` — never for the triage table, and never for a `SKIP`. A dev-harness call that fails outright (for example `find-patient`, which has no failure shape of its own and throws without a live Google Sheets credential) still reports as that scenario's `FAIL` instead of aborting the batch.
- `pnpm run scenarios -- --only <id>` — runs one conversation scenario by id instead of the full batch, e.g. `pnpm run scenarios -- --only hours`.
- `pnpm run scenarios -- --tool-failure` — runs one more scenario, kept out of `conversations.json`, that points `config.google.calendar_id` at an invalid id to exercise `check-availability`'s `calendar_unavailable` path (and the team alert that comes with it) end to end through `process-message`. It backs up `config/config.json` first and restores it afterward, even if the run fails, and never prints the config's contents.
- `node scripts/dev-call.ts <target> '<json>'` — calls the dev-harness webhook (`POST {N8N_URL}/webhook/dev`) directly, for exercising a sub-workflow without WhatsApp. For example, `node scripts/dev-call.ts load-context '{}'` or `node scripts/dev-call.ts notify-team '{"reason":"other","phone":"570000000001"}'`. An unknown target answers `404 {"error":"unknown_target"}`; a request to the webhook without the `X-Dev-Token` header answers `403` (checked against n8n `2.45.6`). `process-message` takes the full contract input (`channel`, `message_id`, `phone`, `name`, `type`, `text`, `received_at`); use `channel: "test"` so its chat memory is keyed `test:<phone>`, which `cleanup` also deletes, and a fresh `message_id` per call, since a repeated one answers `duplicate`. Three targets exist only in the dev harness, not as sub-workflow contracts: `find-patient '{"phone":...}'` looks a row up by exact phone and answers `{ "rows": [...] }`; `cleanup '{"phone_prefix":...}'` deletes a prefix's test data from Calendar, Sheets, and Postgres and is how the scenario runner resets state before and after a run — it refuses any prefix that isn't 8 or more digits with `{"ok":false,"reason":"prefix_too_short"}` before touching anything, and reports `null` for any of its four parts that failed; `retention '{}'` runs `retention-cleanup` directly through its Execute Workflow Trigger. Unlike every other target, `retention` needs no third-party credential (a Schedule Trigger takes none), so it always runs for real instead of reporting a missing-credential failure, answering `{"success":true}` — the Postgres node's own result for a `DELETE` with nothing left to return.
- `node scripts/init-env.ts` — writes `.env` from `.env.example`, filling only the names the local stack and the dev harness need a real value for (`POSTGRES_PASSWORD`, `N8N_DB_PASSWORD`, `APP_DB_PASSWORD`, `APP_RUNTIME_DB_PASSWORD`, `N8N_ENCRYPTION_KEY`, `DEV_HARNESS_TOKEN`) with random hex, and leaving every other blank value (Google, WhatsApp, Anthropic, TypeSafe, ngrok) untouched. Refuses to run if `.env` already exists. The quick start runs this for everyone, not just CI — CI has no repo secrets to fill the file by hand, but a local run gets the same generated local-stack secrets with nothing extra to do.
- `node scripts/check-dev-response.ts` — runs two dev-harness calls and asserts each one's exact response, exiting 1 (with the mismatched response printed, naming which target) on the first mismatch. `retention` must answer exactly `{"success":true}` — `retention-cleanup`'s Postgres-only path, with no Code node on it (`dev-harness`'s own Code nodes, `Count event/row outcomes`, sit on the `cleanup` target's branch instead). `check-availability` with a fixed past date (`{"date":"2020-01-06","phone":"570000000001"}`, a Monday) must answer exactly `{"ok":false,"reason":"past_date"}` — rejected by `Check date`, the *generated* Code node from `src/nodes/compute-free-slots.ts`, before `Decide whether to call Calendar` ever reaches `Get busy events`, so no Google credential is needed either. Together these are CI's `n8n` job proof that n8n actually executes both a plain node path and a generated Code node, not just that the webhook answers something.
- `node scripts/check-db.ts` — runs psql inside the `postgres` container and prints `ok` or `FAIL` per check, exiting 1 on any failure: as `app_runtime`, `CREATE TABLE`, `DROP` and `TRUNCATE` on each granted table, connecting to the `n8n` database, and `SET ROLE` to the owner are all denied with the exact expected error; as the superuser, `app_runtime` holds no role attribute, no membership, no column-level grant beyond its table grants, and no `TEMP` on `app`; `app_runtime`'s privileges on every table and sequence in `public` equal `RUNTIME_GRANTS`, none missing and none extra; every Postgres node's query in `workflows/` runs as `app_runtime`, read straight from the workflow JSON, with `PROBES` binding its `$n` values, inside a transaction it rolls back; and `schema_migrations` records every file in `db/migrations/`. Each check's predicate is unit-tested in `tests/check-db.test.ts`, and a test fails when a new Postgres node has no probe.
- Regenerate a diagram after you edit its source in `docs/diagrams/`. The diagram tool is [archify](https://github.com/tt-a1i/archify), a Node.js command-line tool that needs no install. Keep it outside this repo, so `pnpm run lint` doesn't scan its files, and set `ARCHIFY` to its `bin/archify.mjs`. These sources were last validated, delivered, and exported with archify's 2.17 skill package (`2.17.0-dev.1`). archify v3.2.0 renders the architecture diagram too, but its stricter desktop-readability budget rejects the sequence diagram's small message notes at its 1700 px width. Run the commands from the repo root, because each source's `meta.output` path is relative to it. `architecture.json` has type `architecture`, and `message-sequence.json` has type `sequence`. For the architecture diagram:
  1. `node "$ARCHIFY" validate architecture docs/diagrams/architecture.json --quality showcase --json`, after every edit, until it reports all 9 artifact checks passing with 0 composition errors and 0 warnings.
  2. `node "$ARCHIFY" deliver architecture docs/diagrams/architecture.json docs/diagrams/architecture.html --quality showcase --json` writes the page.
  3. Open the page in a browser, choose **Export**, then **SVG**, and save the download over `docs/diagrams/architecture.svg`, which `README.md` and `docs/architecture.md` embed.
  4. `node "$ARCHIFY" visual-check <copy>.html --json` checks a copy of the page in a real browser at four desktop sizes. It writes PNG screenshots next to the page, so run it on a copy outside the repo.

  For the sequence diagram, run the same steps with type `sequence` and the `message-sequence` files; only `docs/architecture.md` embeds its SVG.
- n8n's `import:workflow`, `export:workflow`, `import:credentials`, `export:credentials`, and `publish:workflow` CLI commands need no owner account, `--userId`, or `--projectId` (checked against `2.45.6`). `publish:workflow` only takes effect after an n8n restart; `pnpm run setup` restarts n8n itself, but only when it actually published something, then waits for `/healthz`, then 15 s more for the publication reconciler, then polls `dev-harness`'s own webhook (the only published workflow with a `webhookPath` in the manifest) until it stops answering 404 — see "Changing a workflow" below.

## Changing a workflow

1. Design the nodes and expressions against n8n's own node reference and real-world examples, especially for a node you haven't configured by hand before.
2. Edit the JSON in `workflows/` (fixed IDs and credential IDs come from `scripts/manifest.ts`), then run `pnpm run build:workflows` to regenerate any Code node it touches.
3. Validate the workflow JSON with an n8n-aware validation tool until it reports no errors.
4. Run `pnpm run setup` to import and publish it against the local n8n instance.
5. Run `pnpm run export` to write n8n's canonical form back to `workflows/` and regenerate Code nodes again. Commit that exported output, not your hand-edited JSON — the two can differ in server-assigned detail, and the exported form is what actually runs.
6. Run the full gate below before committing.

A call made right after `pnpm run setup` restarts n8n can still 404 for a few seconds: `/healthz` reports healthy well before the publication reconciler registers the webhook route for the version just published, which it does on its own schedule (10 s by default). `pnpm run setup` waits 15 s past `/healthz` for exactly this reason, then polls `dev-harness`'s webhook (`scripts/lib/runtime.ts`'s `waitForWebhookLive`, the only manifest entry with a `webhookPath` today) until an unauthenticated POST stops answering 404 — the dev harness's own header-auth check answers 403 once it's genuinely live, needing no credential — failing the whole `setup` run if it's still 404 after a 60 s budget. After any other restart of the `n8n` container, wait the same 15 s before calling a workflow.

## Conventions

- Node 24 LTS, ESM (`"type": "module"`). `tsconfig.json` runs `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `verbatimModuleSyntax`, `erasableSyntaxOnly`, and `allowImportingTsExtensions`, with `noEmit` — there is no build step.
- No `.js` or `.mjs` source files. Scripts are `scripts/*.ts`, run directly with `node scripts/<name>.ts` (Node's native type stripping; no `tsx`). Tests are Vitest files at `tests/**/*.test.ts`. The only JavaScript in the repo is the generated `jsCode` inside workflow JSON.
- CLIs call external programs with `execFile` or `spawn` and an argument array, never a shell string, and guard their entry point with `if (process.argv[1] === fileURLToPath(import.meta.url))` so tests can import their functions without side effects.
- Comments only where intent isn't obvious. A deliberate simplification gets one `NOTE:` line naming its ceiling and upgrade path. A deliberate lint or ShellCheck exception gets a one-line disable comment naming the reason. A comment, doc, or sticky note states its own reason, never a plan task, a ruling, or a review finding's ID; `tests/hygiene.test.ts` scans every tracked file except lockfiles, generated diagram pages, and binaries for them.
- n8n workflow node names are actions (e.g. "Record inbound message"), and sticky notes label each section.
- Every node that calls an external service (Gmail, Google Calendar, Google Sheets, HTTP Request, Postgres, WhatsApp) sets Retry On Fail with 3 tries and a 1000 ms wait, except for the two exceptions the architecture doc's design decisions name (Jev's 2 tries, and the WhatsApp send's 2000 ms wait); `pnpm run check` enforces it. A node whose failure should be visible to the caller (rather than failing the whole run) sets `onError: "continueErrorOutput"` and wires its error output to a response that reports the failure, instead of swallowing it.
- A context or config loader (`load-context`) never names an error workflow of its own. Its callers keep theirs, so a failure while loading context still alerts through the caller. If the loader named the error handler, and the error handler called the loader — as it does, to read `config.team_email` — a missing or unparseable mounted file would loop the two forever: n8n starts the loader's own error workflow on every sub-execution failure, with no guard beyond a workflow naming itself.
- No Code node is hand-written: each is `export function run(input) { ... }` in `src/nodes/<name>.ts` — pure, no I/O, no clock — compiled by `pnpm run build:workflows`; `pnpm run check` rejects any Code node not listed in `scripts/manifest.ts`'s `CODE_NODES`. Those sources use the ambient `DateTime` global (`src/globals.d.ts`) instead of importing Luxon, since the Code-node sandbox provides it but has no `require`; ESLint enforces that by banning `node:*` imports, `luxon`, `process`, and `fetch` in `src/nodes/**`.
- Postgres nodes are typeVersion 2.8 or later wherever a Query Parameters expression can carry text (checked against `2.45.6`'s source and by running it). From 2.8 each `{{ }}` binds exactly one value; 2.5–2.7 still split a string result on commas unless it parses as JSON, so "Hi, I'd like a cleaning, please" would become three values. The n8n-aware validation tool's node database may top out at 2.7 and flag 2.8 as unknown; that's the tool lagging the pinned n8n, not a workflow error.
- An AI Agent node with `onError: "continueErrorOutput"` only uses its error output for failures inside a run (an API error, too many iterations). If it fails before that — a sub-node that can't load, such as a model with a missing credential — n8n sends the agent's input item out of the success output instead. Follow the agent with a check for reply text, as `process-message`'s "Did the agent reply" does, and treat both paths as the failure.
- n8n's Code-node Task Runner (`@n8n/task-runner`) runs generated `jsCode` after setting `Object.defineProperty = () => ({})`, a sandbox hardening measure. esbuild's own IIFE output attaches every named export through that same function, so without a fix every export would silently vanish and `__node.run` would come back `undefined` — this broke the very first Code node this project ran for real (see `build-workflows.ts`'s `hardenAgainstFrozenDefineProperty`, which swaps esbuild's `__defProp` helper for a plain assignment). That rewrite is covered by a dedicated Vitest test that simulates the frozen sandbox; don't remove it when touching the build.

## Languages

Patients get every fixed reply in English or Spanish, and the team gets its emails in one language of its choosing. English is the source language: every key and default string is written in English first, and Spanish is a translation of it.

- **Patient replies.** `process-message`'s `Resolve language` (`src/nodes/resolve-language.ts`) resolves `lang` once per new message: `detectLanguage(text)` from `src/nodes/shared/detect-language.ts`, a deterministic count of Spanish signals (`¿`, `¡`, common Spanish words, and accented words or `ñ`) against common English words that returns `null` unless one side holds at least 60% of them (an accented word it doesn't list, such as a name, only adds to Spanish a listed word or an opening mark already shows), and otherwise `config.locale.default`. A non-text message always uses the default. Every fixed reply node picks `business.replies.<key>[lang]`, `Check reply` replaces and writes its booking confirmation (with the service's `name_i18n` display name and a Luxon date and time in that locale) in `lang`, and `Build system prompt` fills `<<LANGUAGE>>` with a hint: "The patient is writing in Spanish." when detected, or a line naming the default without claiming the patient wrote in it when not. The agent still answers in the language the patient is writing in.
- **Team emails.** `notify-team`'s `Compose alert` and `error-handler`'s `Compose error email` read their labels and alert reasons from `TEAM_MESSAGES` in `src/nodes/shared/team-messages.ts`, picked by `config.team_locale`. What a patient, the agent, or n8n wrote stays as written, and the email stays plain text.
- **Config.** `config.locale.default` (the patients' fallback, `"es"` in the example) and `config.team_locale` (`"en"` in the example) each take `en`, `es`, or any locale `normalizeLocale` (`src/nodes/shared/locale.ts`) reduces to one, such as `es-CO` or `en_US`. A config without either setting, written before they existed, falls back to English for both. Neither setting ever stops a run: an unsupported `locale.default` counts as English in `Resolve language`, which never reads `team_locale`, and `notify-team` and `error-handler` send in English with a line saying `team_locale` is wrong. `tests/runtime.test.ts` checks the example config's values.
- **Service names.** Each service in `business/business.json` keeps its English `name` as the canonical key every tool call, Calendar event, and price lookup uses, plus a `name_i18n` display name per language. The agent's tool descriptions ask for the canonical name, and `validate-booking` maps a translated name back to it in case the model sends one anyway.
- **Switching languages.** Edit `config/config.json`; n8n reads it on every run, so no import or restart is needed. To change what a reply says, edit both of its values in `business/business.json`.
- **Adding a language**, for example Portuguese:
  1. Add `'pt'` to `Lang` and `LANGS` in `src/nodes/shared/locale.ts`, and let `normalizeLocale` accept it.
  2. Add a `pt` value to every reply and every service's `name_i18n` in `business/business.json`, a `pt` entry to `TEAM_MESSAGES`, to `check-reply.ts`'s `CONFIRMATIONS`, and to `build-system-prompt.ts`'s `LANGUAGE_NAMES`. `tsc` flags every `Record<Lang, …>` table still missing it, and `tests/content.test.ts` and `tests/nodes/team-messages.test.ts` fail on any reply or message missing or empty.
  3. Teach `detect-language.ts` the new language's signals and decide how it ranks against the others; add its cases to `tests/nodes/detect-language.test.ts`.
  4. Run `pnpm run build:workflows` and the full gate, and commit the regenerated workflow JSON.

## Guardrails

- Secrets live only in `.env` (gitignored) and n8n credentials — never in code, workflow JSON, or committed config.
- Test data uses phone numbers with the `5700000000` prefix and emails on `example.com`; never a real person's data. The dev harness's `cleanup` target deletes by that same prefix across Calendar, Sheets, and Postgres (`starts_with`, never `LIKE`, so a non-digit or under-8-digit prefix is refused rather than silently matching everything).
- Everything in the repo is in English, except the Spanish translations (each `es` value in `business.json`'s `replies` and in the `{ en, es }` tables in `src/nodes/`), the Spanish word list language detection scores, and test inputs that deliberately exercise the assistant's Spanish replies (the triage fixture set, the Spanish conversation scenarios, and the adversarial inputs `docs/red-team.md` lists) — that Spanish text is intentional, not a rule violation. No other Spanish string belongs in source logic.
- Database topology: role `n8n` owns database `n8n`, role `app` owns database `app` and its tables, and neither can connect to the other's database (`REVOKE ALL ... FROM PUBLIC`). Every Postgres node connects through the `App DB` credential as `app_runtime`, which has DML on named tables only: no DDL in `app`, no `TRUNCATE`, and no access to `n8n`. The one exception is the Postgres Chat Memory node, which runs `CREATE TABLE IF NOT EXISTS` on every execution and so connects as `app` through its own `App DB (chat memory)` credential; `tests/tooling.test.ts` pins it as that credential's only user (`docs/database.md` has the evidence). The Postgres superuser exists only for `db/init/` and `db-migrate`; it is never configured in the n8n container and should never reach it. A new table gets its grants in its own migration, never through default privileges.
- Every workflow sets `settings.saveManualExecutions: false`, and `tests/workflows/execution-data.test.ts` asserts it for every file in `workflows/`. There's no per-workflow exception: even a workflow that only reads config, such as `load-context`, starts from a `passthrough` Execute Workflow Trigger whose callers send no input schema, so it receives its caller's whole item, patient data and tokens included.
- n8n is pinned to `2.45.6`; never move to an unstable `3.x` tag before one is stable. Dependabot's automated updates for `n8nio/n8n` exclude minor and major bumps, because beta and stable releases share plain semver tags.
- Point tooling only at this repo's local n8n instance (`http://localhost:5678`), never another instance.
- No script prints credential data — `setup-credentials.ts` detects which credentials already exist in n8n from a CLI export, never a decrypted one, and only ever logs a credential's name, never its `data`. Credentials go in over stdin and the existing-credentials id listing comes out over stdout; nothing credential-related touches the host filesystem or the `.n8n-import/` bind mount (a `sh -c` script makes its own temp file in the container's own `/tmp` for each direction and removes it).
- Any email sent to the team (e.g. `notify-team`, the error handler) is plain text, never HTML — so text a patient typed can't inject markup into a staff inbox.
- Agent tools never take the phone number from the model: each tool node maps `phone` from the workflow's own trigger (`$('When called').first().json.phone`), and any sub-workflow input the model shouldn't fill is mapped or marked removed, because a tool node passes the model's raw arguments through to unmapped fields. `tests/workflows/process-message.test.ts` pins the phone mapping and each tool's `$fromAI` keys against an allowlist, and fails when a sub-workflow input is neither mapped nor removed. `notify_team`'s `reason` is clamped to `unknown_treatment`, `out_of_scope`, or `other`, because `notify-team` exempts `tool_failure` alerts from its per-phone cooldown and lets only an earlier emergency hold back an `emergency` alert.
- Every Gmail node sends plain text and every Google Sheets write stores values raw (`cellFormat: RAW`), so text a patient typed can't inject markup into a staff inbox or a formula into the Patients sheet. No Gmail node sets a sender name: n8n's Gmail node then reads the account profile, which the send-only scope doesn't allow, so every send would fail. `tests/workflows/injection-guards.test.ts` pins all three.
- `scripts/export-workflows.ts`'s `normalizeWorkflow` strips fields n8n sets on export that reflect this instance's own history rather than the workflow's source (pinned data, timestamps, `active`, `versionCounter`, …). Importing and exporting the same workflows twice in a row must produce no diff; if n8n starts emitting a new such field, add it to that drop list and to its test.

## Supply-chain hardening

Package management is pnpm, pinned in `package.json`'s `packageManager` to an exact `11.x` version; never move to pnpm 12 (Dependabot's dependency-graph parser does not yet read its default two-document lockfile). `pnpm-workspace.yaml` holds the settings pnpm 11 no longer reads from `.npmrc`:

- `minimumReleaseAge: 4320` — refuses to install any package version (including transitive) published less than 3 days ago, so a newly-compromised release has a window to be caught and pulled before this repo can pull it in.
- `minimumReleaseAgeExclude: []` — pnpm 11 ships a default exclusion list for `n8n`/`n8n-*`/`@n8n/*`; this repo overrides it with an empty one, so no package is exempt from the age gate above.
- `trustPolicy: no-downgrade` — fails an install if a package's trust evidence (provenance/trusted publishing) regresses from an earlier release, or if the pinned pnpm version itself would downgrade that evidence.
- `blockExoticSubdeps: true` — only a direct dependency may resolve from a git or tarball URL; every transitive dependency must come from the registry.
- `strictDepBuilds: true` with `dangerouslyAllowAllBuilds: false` — a dependency's install/postinstall script fails the install unless it's explicitly approved in `allowBuilds`; nothing runs by silent default.
- `engineStrict: true` — a dependency whose `engines` range excludes this repo's Node fails the install instead of warning.
- `allowBuilds` lists only packages a real `pnpm install --frozen-lockfile` proved need their build script, each with a one-line reason. Check `esbuild: true` (its postinstall re-links the platform-specific `optionalDependencies` binary over the `bin/esbuild` JS shim) as the one-entry example; add another only after the same proof.

`tests/supply-chain.test.ts` reads these back through `pnpm config list --json` — pnpm's effective config, not the YAML text — so a misspelled key or a value pnpm silently ignores fails the test. It also asserts `packageManager`'s exact-pnpm-11 shape, that `package-lock.json` doesn't exist, that no tracked file still teaches an `npm` command, that every Compose `image:` line and every image a CI workflow runs with `docker run` carries a `@sha256:` digest, that CI installs zizmor only with `--require-hashes`, and that every long-running Compose service sets `no-new-privileges`, with `n8n` (and so `n8n-worker`) dropping every capability.

**Updating a dependency:** edit `package.json`, run `pnpm install` (not `--frozen-lockfile`) to update `pnpm-lock.yaml`, run the gate below, and commit both files together. `minimumReleaseAge` will refuse a version published too recently — that's a feature, not a bug to work around; wait it out or pin an older compatible version.

**Landing a security fix younger than the 3-day gate:** a patched version sometimes ships less than 3 days before you need it in. To install it anyway:
1. Add a temporary entry to `pnpm-workspace.yaml`'s `minimumReleaseAgeExclude`, scoped to that one package and version (pnpm accepts `name@version`, e.g. `"esbuild@0.28.3"` — not the bare package name, which would exempt every future version too), with a `#` comment naming the advisory ID and today's date.
2. Run `pnpm install` and merge as usual.
3. Remove the entry once that version is older than 3 days.

`tests/supply-chain.test.ts` asserts `minimumReleaseAgeExclude` is empty, so it goes red the moment step 1 lands — on purpose: the failing test is the reminder to do step 3. Let the test stay red for that one PR's lifetime rather than weakening the assertion for everyone; if that would make CI unmergeable, the simpler rule is to wait out the 3-day gate instead of landing it early, since this repo's own traffic rarely needs the override badly enough to justify a widened test.

**Images** (`compose.yaml`, `compose.queue.yaml`) are pinned `name:tag@sha256:<digest>`, the multi-arch index digest from `docker buildx imagetools inspect name:tag`, so the same reference resolves correctly on both arm64 (local) and amd64 (CI). Dependabot keeps an existing digest current as new builds of that tag are published, but won't add one that isn't there — a tag bump still needs the digest re-resolved the same way and the tag reviewed by hand first.

**CI tool images and zizmor** are pinned the same way, by hand, because Dependabot reads neither a `docker run` line nor `.github/zizmor-requirements.txt`. To bump a tool image, review the new tag, resolve its index digest with `docker buildx imagetools inspect name:tag`, and replace the whole `name:tag@sha256:<digest>` reference in `.github/workflows/ci.yml`. To bump zizmor, take every file's `sha256` for the new version from `https://pypi.org/pypi/zizmor/<version>/json` and replace the version and all the hashes in `.github/zizmor-requirements.txt`.

**CI** installs with `pnpm/setup` (pinned by commit SHA) then `actions/setup-node` with `cache: pnpm`, then `pnpm install --frozen-lockfile`, then `pnpm audit --audit-level=high`.

**The `n8n` job** (`.github/workflows/ci.yml`) is the one job that boots the real stack and proves a workflow executes — both a plain node path and a generated Code node — not just that the committed JSON is well-formed. It runs `node scripts/init-env.ts` (CI has no repo secrets, so `.env` is generated, not copied by hand) and `cp config/config.example.json config/config.json`. No credential data ever touches the `.n8n-import/` bind mount (see that directory's own entry in Repo map above), so the job needs no CI-only permissions step for it — the runner's uid (1001) and n8n's own uid (1000) inside the container never need to read or write the same file there. It brings up only `postgres` and `n8n` (`--wait`), runs `pnpm run setup` (which migrates first), then `node scripts/check-db.ts` (the runtime role's denials, its exact grants, every workflow statement, and the migration ledger), then `node scripts/check-dev-response.ts` (which also proves `app_runtime`'s grants hold for a real n8n run), and tears down with `docker compose down -v` in an `if: always()` step — CI's volumes are disposable, unlike a local stack's. What CI doesn't run, and why: `pnpm run scenarios` (needs real TypeSafe, Anthropic, and Google credentials CI doesn't have), the queue-mode stack (`compose.queue.yaml`, which needs no credential but adds nothing `check-dev-response.ts` doesn't already prove about plain-node and Code-node execution), and every other harness target whose workflow needs a third-party credential.

**Dependabot** (`.github/dependabot.yml`) adds a 7-day cooldown to every ecosystem, beyond GitHub's own platform-wide default: `npm` (which also covers the pnpm lockfile) gets semver-tiered days (14 major, 7 minor, 7 patch); `docker-compose` and `github-actions` get a flat `default-days: 7`, since neither has a universal semver convention for "major/minor/patch". Dependabot waits 7 days before proposing a version update, so every version PR is already past pnpm's 3-day `minimumReleaseAge` install gate — it never arrives asking to install a version the gate would still refuse. Security updates are proposed immediately, cooldown-free, since Dependabot never delays those.

## Definition of done

- `pnpm run typecheck && pnpm run lint && pnpm test && pnpm run build:workflows -- --check && pnpm run check` all pass locally — run this full gate before every commit that touches TypeScript.
- No secrets anywhere in the diff or git history; `.env` and `config/config.json` are never committed.
- `README.md` (Status, What works now, and the quick start if commands changed) and this file are updated to match what the change actually adds.
- Commits follow Conventional Commits.
