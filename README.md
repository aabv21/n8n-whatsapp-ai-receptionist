# Cumbident WhatsApp AI Receptionist

**Demo**

An n8n WhatsApp assistant that answers a dental studio's questions, books appointments in Google Calendar, and hands patients to staff when needed.

![System architecture: WhatsApp reaches n8n through a one-path ngrok tunnel, and n8n's workflows call Postgres, Google, Anthropic, and TypeSafe](docs/diagrams/architecture.svg)

The [architecture doc](docs/architecture.md) follows a message from webhook to reply, lists what each failure does, and explains the design decisions. The [red-team doc](docs/red-team.md) maps where a patient's text reaches a model, lists the adversarial inputs the assistant is checked against, and names the guard behind each one.

## Status

In progress: local runtime, toolchain, workflow tooling/CI, the business content and system prompt, the platform workflows every other workflow relies on, the business tools `check-availability`, `upsert-patient`, and `book-appointment`, Jev-based message triage, `process-message` (the core every patient message runs through), a conversation-scenario eval suite that drives it through scripted, multi-turn conversations, `whatsapp-entry`, the WhatsApp webhook entry point in front of it, `retention-cleanup`, a daily job that prunes old messages and chat memory from Postgres, an optional queue-mode Compose override that moves executions onto separate worker containers, the architecture doc with its system and message-lifecycle diagrams, a least-privilege database runtime role with numbered migrations, documented in the database doc, and a red-team doc that maps each adversarial input to the guard that handles it.

### What works now

- A strict TypeScript toolchain: `typecheck`, `lint`, and `test` scripts.
- The local runtime: Postgres and n8n in Docker Compose, with separate database roles for n8n and the application.
- A least-privilege database setup ([docs/database.md](docs/database.md)). Every Postgres node connects as `app_runtime`, which has DML only on the app's two tables: no DDL in `app`, no `TRUNCATE`, and no access to n8n's database. The Postgres Chat Memory node is the documented exception: it runs `CREATE TABLE IF NOT EXISTS` on every execution, so it connects as the owner role. Schema changes ship as numbered, idempotent files in `db/migrations/`, which `pnpm run db:migrate` applies once each, and `pnpm run setup` runs it first. The migrations add a `CHECK` on `inbound_messages.route` and an index on `received_at` for the daily retention delete. `node scripts/check-db.ts` proves in CI that the runtime role's forbidden statements fail, that its privileges equal the grant list, and that every workflow's SQL runs under it. Every workflow sets `saveManualExecutions: false`, so a run started from the editor never keeps a patient's data or a token. The doc also covers retention, a backup restored and checked by row counts, and the upgrade path for an existing local volume.
- An optional `tunnel` profile that exposes n8n through ngrok, restricted to forwarding only the WhatsApp Trigger's own fixed webhook path, not any webhook-shaped one, rate-limited per client IP, and with ngrok's request inspection off. n8n refuses any request body over 2 MiB.
- Workflow tooling: a manifest of fixed workflow and credential IDs, hygiene checks that reject pinned data, literal secrets, and hand-written Code nodes, and a Code-node build that compiles `src/nodes/*.ts` into Code-node JavaScript with esbuild — hardened so a node's exports survive n8n's Code-node sandbox, which runs generated code with `Object.defineProperty` disabled.
- Scripts to set up credentials and import, export, and publish workflows against the local n8n instance, plus a dev-harness client for calling a sub-workflow directly during offline testing.
- A GitHub Actions pipeline: the full quality gate, ShellCheck, gitleaks, `pnpm audit`, actionlint, zizmor, a CodeQL scan (turns on once the repo is public), and an `n8n` job that boots the real stack with a generated `.env`, runs `check-db` against the runtime role, and proves two workflows execute end to end through the dev harness, with no WhatsApp, Google, Anthropic, or TypeSafe credential: `retention`'s Postgres-only path, and `check-availability` rejecting a fixed past date through its own generated Code node (`Check date`, from `src/nodes/compute-free-slots.ts`) before any Calendar call. CI doesn't run `pnpm run scenarios` (needs real TypeSafe, Anthropic, and Google credentials), the queue-mode stack, or any other harness target that needs a third-party credential — see AGENTS.md's "The `n8n` job" section.
- Supply-chain hardening: pnpm with a release-age gate, trust-policy enforcement, blocked exotic sub-dependencies, and build-script approval (`pnpm-workspace.yaml`); every Compose image, and every image CI runs with `docker run`, pinned by digest; zizmor installed in CI only from hash-pinned requirements; every long-running container started with `no-new-privileges`, and `n8n` with every Linux capability dropped; the Gmail credential limited to sending; a Dependabot cooldown on every ecosystem — see AGENTS.md's "Supply-chain hardening" section.
- Business content the workflows load at runtime: `business/business.json` (the facts — address, hours, prices, payment methods, fixed replies), `business/knowledge-base.md` (FAQ prose), and `prompts/system-prompt.md` (the assistant's system prompt template, with `<<BUSINESS>>`, `<<KNOWLEDGE_BASE>>`, `<<NOW>>`, and `<<TRIAGE_NOTES>>` placeholders), all checked by `tests/content.test.ts`.
- The four platform workflows every other workflow depends on: `load-context` (reads the business content above into one item), `error-handler` (emails the team when any other workflow fails), `notify-team` (alerts the team by email for a flagged conversation, at most once per phone per `config.limits.alert_cooldown_minutes`, except for `tool_failure` alerts, so one phone can't use up the Gmail daily quota that real emergencies rely on; an emergency is held back only by an earlier emergency, never by an earlier alert of another kind), and the token-protected `dev-harness`, which lets `node scripts/dev-call.ts <target> '<json>'` call any of these directly over HTTP without WhatsApp or the n8n editor.
- `check-availability`: computes open appointment slots from the business's hours, minimum notice, and Google Calendar's busy events (`src/nodes/compute-free-slots.ts`, unit-tested). Before calling Calendar, a "Check date" step re-runs that same logic with no events, so an invalid, past, or closed date is rejected offline without an avoidable API call; only a valid, open date reaches Calendar. A Calendar failure alerts the team through `notify-team` and reports `calendar_unavailable`.
- `upsert-patient`: validates `phone` and `status`, then appends or updates the matching row (by phone) in the Patients Google Sheet. It looks the row up first and merges in the new fields, so a call that only sends `status` doesn't blank out a `name` or `last_appointment` a previous call stored, and an `inquiry` update keeps a stored status rather than downgrading a `booked` or `handed_off` patient; cell values are written raw so `phone` round-trips as the exact string, never a reformatted number. A Sheets failure alerts the team through `notify-team` and reports `sheets_unavailable`. The dev harness also gained `find-patient` (a phone lookup that answers `{ "rows": [] }` for a patient with no row yet) and `cleanup` (deletes one phone prefix's test data from Calendar, Sheets, and Postgres — refusing, before touching anything, a prefix that isn't 8 or more digits — with `null` for any one of its four independent parts that failed).
- `book-appointment`: validates the service, date, time, opening hours, the slot grid, minimum notice, and the booking horizon of `config.limits.max_booking_days_ahead` days entirely offline (`src/nodes/validate-booking.ts`, unit-tested) before Calendar is ever called, with the same ordered-checks approach as `check-availability`. Only a valid request then reads the phone's upcoming bookings from Calendar and reruns the same checks with that count, so a phone that already has `config.limits.max_upcoming_bookings` upcoming bookings gets `too_many_bookings`. Only a valid request re-checks the exact `[start, end)` slot in Calendar (Recurring Event Handling "expand", Always Output Data so an empty result doesn't stop the branch); any event already in that window answers `slot_taken` instead of double-booking it. Otherwise it creates the Calendar event, upserts the patient as `booked` with `last_appointment` set to the new start time, and returns the event id, start, end, service, and price. A Calendar failure alerts the team through `notify-team` and reports `calendar_unavailable`.
- `triage-message`: asks TypeSafe's Jev model (`jev-1.14.0`) five yes/no questions about the latest patient message and up to 3 earlier ones — `emergency`, `asks_for_human`, `complaint`, `medical_advice`, `manipulation` — then applies `config.triage.thresholds` to pick one route: `blocked` (manipulation, which overrides everything else), `emergency`, `handoff` (asks a human or complains), or `agent`, plus flags and agent-facing notes (`src/nodes/decide-route.ts`, unit-tested). It fails open: a Jev request that errors, times out, or answers incompletely — any score missing, non-numeric, or outside `[0, 1]` — returns `scores: null`, `route: "agent"`, and `flags.triage_failed: true`, so a TypeSafe outage can never block a reply. `node scripts/run-scenarios.ts --triage` grades a 17-item English/Spanish evaluation set (`tests/scenarios/triage.json`) against the live model and prints a per-language, per-signal accuracy table, once a real TypeSafe credential exists.
- `process-message`: the core every patient message runs through. It records the message in Postgres first, so a repeated `message_id` (Meta redelivering a webhook) answers `duplicate` with no reply and no second agent run. A non-text or whitespace-only message gets a fixed reply; a phone that sends more than `config.limits.max_messages_per_window` text messages in `config.limits.window_minutes` gets one rate-limit notice, then silence. Text is cut to `config.limits.max_text_chars` characters, never mid-character, and triaged with up to 3 earlier messages. `blocked` gets a fixed reply. `emergency` and `handoff` alert the team first (a handoff also marks the patient `handed_off`), and the agent still replies to them, as it does to every other message. The agent is Claude Haiku 5.5 with Postgres chat memory and four tools — `check_availability`, `book_appointment`, `upsert_patient`, `notify_team` — that always take the phone number from the incoming message, never from the model, and its prompt says the team was alerted only when that alert actually sent, not when the cooldown held it back. The `notify_team` tool can only send the reasons `unknown_treatment`, `out_of_scope`, or `other`, and a handoff marks the patient without overwriting the name they gave. Before a reply goes out, `src/nodes/check-reply.ts` replaces one that gives a dose or names a medicine with the fixed `medical_advice` reply, and one that offers a discount or quotes a peso amount that isn't a listed price with the fixed `price_check` reply; a replacement still confirms any appointment booked that turn, with its service, date, and time. The system prompt is filled by `src/nodes/build-system-prompt.ts` and the tool results collected by `src/nodes/collect-tool-calls.ts` (both unit-tested). If the agent fails, `notify-team` sends the team a `tool_failure` alert, and the patient gets the fixed `technical_issue` reply (route `fallback`), or `technical_issue_retry`, which doesn't say the team was notified, when that alert didn't send. It returns `{ reply, route, flags, tool_calls }`.
- Conversation scenarios: `tests/scenarios/conversations.json` holds 20 scripted, multi-turn conversations — opening hours, a cleaning price quote, booking tomorrow's first slot, a Sunday request, an out-of-scope question, asking for a person, a dental emergency, a returning patient, a relative date ("next Thursday"), a patient asking the assistant to store a different phone number, a Spanish reply, and nine adversarial inputs from the [red-team doc](docs/red-team.md): an instruction override, prompt extraction, another patient's data, booking past the per-phone limit, an invented discount, a dose request, an injection aimed at triage, context poisoning across turns, and a cancellation — each checked turn by turn against its expected route, tools called or excluded, reply text, and tool input/output (`scripts/lib/scenarios.ts`'s `checkTurn`, `nextWeekday`, and `resolveTokens`). `pnpm run scenarios` prints the triage accuracy table and then a `| id | result | details |` row per conversation, exiting 1 on any conversation `FAIL` (never for the triage table, and never for a `SKIP`, which a scenario needing tomorrow open prints instead of running on a Sunday in America/Bogota); `--only <id>` runs a single scenario, and `--tool-failure` runs one more scenario (kept out of the fixture file) that temporarily points `config.google.calendar_id` at an invalid id to exercise `check-availability`'s `calendar_unavailable` path, restoring the config afterward even if the run fails. Offline, with no Anthropic key, every conversation reports `FAIL`, because `process-message` can only reach route `fallback` — the real pass is the live integration check.
- `whatsapp-entry`: the thin entry point between Meta's webhook and `process-message`. The WhatsApp Trigger (subscribed to `messages` only, with status updates — sent/delivered/read/failed — turned off so none of them start an execution) delivers one item per change; `process-message` runs once per change (`mode: each`), not merged into a single run per batch. "Is there a message" also stops a reaction (a thumbs-up added or removed) or a system message (e.g. a changed number) the same way it stops an item with no `messages` array at all — no reply, nothing recorded. A real message is normalized into `process-message`'s contract — `channel: 'whatsapp'`, the Unix-seconds `timestamp` converted to an ISO string with Luxon, `name` `null` when WhatsApp sent no `contacts` block, `text: ''` and `type: 'other'` for anything but plain text — reading only `messages[0]` even when a single change's `messages` array carries more. `process-message`'s reply, when not `null`, goes out through a WhatsApp send (3 tries, 2000 ms apart — a fixed exception to this project's usual 1000 ms wait); only a send that actually succeeds marks the message's `replied_at`, which means WhatsApp accepted the send, not that the patient's device delivered or read it. An unexpected failure — a Postgres outage or an unexpected error — reaches no patient reply and instead fails into the error workflow, which emails the team. The tunnel's traffic policy allows through only this trigger's own fixed webhook path, so Meta's GET verification (which carries `hub.*` query parameters, excluded from the path ngrok matches against) and its POST deliveries both reach n8n, and nothing else does.
- `retention-cleanup`: a daily job, 03:00 America/Bogota, that deletes old data from Postgres so the database doesn't grow without bound. It loads `config.limits.retention_days` through `load-context`, then deletes chat memory before messages: an `n8n_chat_histories` row is kept only while `inbound_messages` still has a row for that session's phone (bare for WhatsApp, `test:`-prefixed for the test channel) inside the retention window, so memory is judged against messages that are still there when it runs; `inbound_messages` itself is pruned last, by `received_at`. Both deletes set Always Output Data, since a bare `DELETE` with no `RETURNING` clause would otherwise report zero rows affected as zero items and stop the run. Alongside its Schedule Trigger, an Execute Workflow Trigger lets the dev harness's `retention` target run the same job on demand; needing only Postgres, it's the one dev-harness call that always runs for real rather than reporting a missing-credential failure.
- An optional queue-mode override, `compose.queue.yaml`: adds Redis and one or more `n8n-worker` containers so executions run off the main process. `n8n-worker` extends `compose.yaml`'s own `n8n` service, so it keeps the same encryption key, database settings, and read-only `/files` mounts the main process has, and `ports: !reset []` keeps it from publishing a host port, so it scales past one replica without a conflict. See "When you'd need queue mode" below.
- `docs/architecture.md`: the components, the message lifecycle, the data model, a failure-modes table, scaling and security notes, and the design decisions, each one stating what it chose over what. Its two diagrams, the system architecture and the message sequence, come from `docs/diagrams/*.json` through archify, and `AGENTS.md` shows how to regenerate them.

## Quick start

```bash
node scripts/init-env.ts
cp config/config.example.json config/config.json
pnpm install --frozen-lockfile
docker compose up -d --wait
pnpm test
```

`init-env.ts` writes `.env` from `.env.example`, filling only the local-stack secrets (`POSTGRES_PASSWORD`, `N8N_DB_PASSWORD`, `APP_DB_PASSWORD`, `APP_RUNTIME_DB_PASSWORD`, `N8N_ENCRYPTION_KEY`, `DEV_HARNESS_TOKEN`) with random hex. Every external credential (Google, WhatsApp, Anthropic, TypeSafe, ngrok) stays blank — fill those in by hand before the workflow that needs them will work for real.

Already have a local stack from before `db/migrations/` existed? Keep its volume. Add the two `APP_RUNTIME_DB_*` lines to your `.env` instead of regenerating it, then run `pnpm run setup`. The database doc's [upgrade steps](docs/database.md#upgrading-an-existing-local-stack) show how to add them without printing the password.

Once n8n is up, `pnpm run setup` applies any pending database migrations, imports whichever credentials already have their `.env` values filled, and publishes the workflows in `workflows/`; a workflow whose trigger needs a credential that isn't filled in yet (Google, WhatsApp) is held back rather than published half-configured. With no Google credentials, try the platform workflows directly:

```bash
node scripts/dev-call.ts load-context '{}'
node scripts/dev-call.ts notify-team '{"reason":"other","phone":"570000000001","summary":"Test alert"}'
node scripts/dev-call.ts check-availability '{"date":"<a Sunday>","phone":"570000000001"}'
node scripts/dev-call.ts check-availability '{"date":"<a weekday>","phone":"570000000001"}'
node scripts/dev-call.ts upsert-patient '{"phone":"570000000001","status":"inquiry"}'
node scripts/dev-call.ts cleanup '{"phone_prefix":"57"}'
node scripts/dev-call.ts cleanup '{"phone_prefix":"5700000000"}'
node scripts/dev-call.ts book-appointment '{"phone":"570000000001","name":"Test Patient","service":"Dental implants","date":"<next Wednesday>","time":"09:30"}'
node scripts/dev-call.ts book-appointment '{"phone":"570000000001","name":"Test Patient","service":"Dental cleaning","date":"<next Wednesday>","time":"09:30"}'
node scripts/dev-call.ts triage-message '{"text":"Can I please talk to a real person?","recent_messages":[]}'
node scripts/dev-call.ts process-message '{"channel":"test","message_id":"t-1","phone":"570000000002","name":"Test","type":"text","text":"How much is a dental cleaning?","received_at":"<now, as ISO 8601>"}'
node scripts/dev-call.ts retention '{}'
pnpm run scenarios -- --only hours
```

The `notify-team` call answers `{"ok":false,"reason":"email_failed"}` until a real Gmail credential exists, and the second `check-availability` call answers `{"ok":false,"reason":"calendar_unavailable"}` until a real Google Calendar credential exists — those are the expected offline results, not a bug. The Sunday call answers `{"ok":false,"reason":"closed"}` without needing Calendar at all. The `upsert-patient` call answers `{"ok":false,"reason":"sheets_unavailable"}` the same way, until a real Google Sheets credential exists. `cleanup '{"phone_prefix":"57"}'` is refused (`prefix_too_short`) before touching anything; `cleanup '{"phone_prefix":"5700000000"}'` runs its two Postgres deletes for real and answers with their counts, with `null` for the Calendar and Sheets parts until those credentials exist. The first `book-appointment` call answers `{"ok":false,"reason":"invalid_service"}` without touching Calendar; the second, a valid request, answers `{"ok":false,"reason":"calendar_unavailable"}` the same way as `check-availability`, until a real Google Calendar credential exists. The `triage-message` call answers `scores: null`, `route: "agent"`, and `flags.triage_failed: true` until a real TypeSafe credential exists — triage fails open rather than risk blocking a reply. The `process-message` call answers `route: "fallback"` with the fixed `technical_issue_retry` reply until real Anthropic and Gmail credentials exist: triage fails open, the agent can't reach Claude, and the team alert can't send, so the reply doesn't claim the team was notified. Running it again with the same `message_id` answers `{"reply":null,"route":"duplicate","flags":{},"tool_calls":[]}`. The `retention` call needs no external credential, so it runs for real and answers `{"success":true}`, the Postgres node's own result for a `DELETE` with nothing left to return — run it after seeding Postgres with an old `inbound_messages` row to see it actually prune one. `pnpm run scenarios -- --only hours` runs the `hours` conversation scenario through `process-message` the same way and reports it `FAIL`, with its details naming route `fallback`, for the same reason; `pnpm run scenarios` runs the full triage-and-conversation suite, and `AGENTS.md` describes `--only <id>` and `--tool-failure`. See `AGENTS.md` for the full command list.

## Upgrading an existing setup

Pulling this version into a checkout that already has a `config/config.json`, a local stack, or signed-in Google credentials takes three steps:

1. **Add the new limits to `config/config.json`.** Copy `alert_cooldown_minutes`, `max_booking_days_ahead`, and `max_upcoming_bookings` from `config/config.example.json` into your own file's `limits`. Without a valid `alert_cooldown_minutes`, every alert except `tool_failure` stops with an error that `error-handler` emails to the team. Without either booking key, every booking fails closed the same way, before any Calendar call. A `config.triage.thresholds` value that's missing or outside (0, 1] now fails triage with an error email too, instead of silently turning that signal off.
2. **Narrow the Gmail sign-in to sending.** `pnpm run setup` re-imports only non-OAuth credentials: it skips a Google Calendar, Google Sheets, or Gmail credential that already exists, so an existing Gmail credential keeps n8n's default full-mailbox scopes. In the n8n editor, open the **Gmail** credential, turn on **Custom Scopes**, set **Enabled Scopes** to `https://www.googleapis.com/auth/gmail.send`, save, and sign in with Google again. (`node scripts/setup-credentials.ts --force` re-imports every credential from `.env` instead, which signs out all three Google credentials.) The old token's broad grant stays valid until you remove the app under your Google Account's [third-party access](https://myaccount.google.com/connections); that signs out all three Google credentials, so sign each one in again afterward.
3. **Recreate the containers.** `docker compose up -d --wait` recreates `postgres` and `n8n` with `no-new-privileges`, `n8n`'s dropped capabilities, and its 2 MiB request cap, keeping the named volumes. Add the same flags you start the stack with: `docker compose --profile tunnel up -d --wait` recreates `ngrok` too, with inspection off and the traffic policy's new rate limit, and `docker compose -f compose.yaml -f compose.queue.yaml up -d --wait --scale n8n-worker=2` recreates `redis` and the workers.

## Pending live checks

CI's `n8n` job boots `postgres` and `n8n` with the hardened container settings and runs every workflow statement as the runtime role, but these need credentials or services CI doesn't have:

- the live adversarial scenarios and the dev-harness checks in the [red-team doc](docs/red-team.md), including the alert cooldown and an emergency after an alert of another kind, both against real Gmail, and the booking limit against real Calendar;
- the `tunnel` profile, with `ngrok` running under `no-new-privileges`;
- through the public ngrok URL, `/`, `/rest/login`, `/webhook-test/x`, `/webhook/dev`, and `//webhook/x` each answer 404, and only the WhatsApp Trigger's own path reaches n8n, Meta's verification GET included;
- a burst of unsigned POSTs to the trigger's path gets HTTP 429 once it passes the policy's 60 a minute, a real WhatsApp message right after still gets its reply, and ngrok's inspection interface shows no captured request;
- a POST to the trigger's path with a body over 2 MiB is refused (HTTP 413) and starts no execution;
- queue mode (`compose.queue.yaml`), with `redis` under `no-new-privileges` and `n8n-worker` inheriting `n8n`'s dropped capabilities;
- a Gmail sign-in limited to `gmail.send`, sending an alert and an `error-handler` email.

## When you'd need queue mode

The default stack runs n8n as a single process that both receives WhatsApp webhooks and runs every execution, enough for this demo's traffic. Reach for `compose.queue.yaml` when:

- **One process runs short of CPU or memory**: executions already run concurrently, so that process's CPU and memory are the limit; see the architecture doc's [scaling section](docs/architecture.md#scaling-limits-and-what-to-change).
- **Horizontal scaling** is worth it: worker count (`--scale n8n-worker=N`) grows independently of the main instance, which keeps receiving webhooks throughout.

The trade-off is cost: a Redis container plus one or more worker containers to run, monitor, and keep healthy — overhead this demo's own traffic doesn't justify today.

```bash
docker compose -f compose.yaml -f compose.queue.yaml up -d --wait --scale n8n-worker=2
```

Return to the regular stack with `docker compose -f compose.yaml -f compose.queue.yaml down && docker compose up -d --wait` — plain `down`, with no `-v`, keeps the named volumes.
